# 子智能体架构方案 — 深度思考

> **日期**: 2026-04-21 | **思路**: 将 TradingAgents-CN 的 12 个角色改造成子智能体，支持互相通信
> **参考**: learn-claude-code 的 s04（子代理）+ s09-s11（团队通信）

---

## 一、核心思路

```
现在的 TradingAgents-CN:
  1个父进程 + LangGraph状态图 + 12个角色串行执行
  角色之间通过"共享状态"传数据（不直接通信）

改造后的方案:
  1个父智能体（编排者）+ N个子智能体（各角色）+ 消息总线（通信）
  子智能体之间可以直接通信（辩论、协商）
```

---

## 二、架构设计

### 2.1 整体结构

```
┌─────────────────────────────────────────────────────────────┐
│                     父智能体（编排者）                         │
│                                                               │
│  职责: 接收任务、派活给子智能体、汇总结果                       │
│  不做具体分析，只做调度                                       │
│                                                               │
│  "分析300033"                                                │
│    ↓                                                          │
│  派活给子智能体们...                                          │
│    ↓                                                          │
│  收集结果，输出最终决策                                       │
└───────────┬────────────┬────────────┬───────────────────────┘
            │            │            │
     ┌──────┴───┐  ┌─────┴────┐  ┌───┴──────────┐
     │ 分析师团队 │  │ 研究团队  │  │   风控团队    │
     │           │  │          │  │              │
     │ ┌───────┐ │  │ ┌──────┐ │  │ ┌──────────┐ │
     │ │技术面  │ │  │ │看多   │←→│ │激进      │ │
     │ └───────┘ │  │ └──────┘ │  │ └──────────┘ │
     │ ┌───────┐ │  │ ┌──────┐ │  │ ┌──────────┐ │
     │ │基本面  │ │  │ │看空   │←→│ │保守      │ │
     │ └───────┘ │  │ └──────┘ │  │ └──────────┘ │
     │ ┌───────┐ │  │ ┌──────┐ │  │ ┌──────────┐ │
     │ │新闻    │ │  │ │经理   │  │ │中性      │ │
     │ └───────┘ │  │ └──────┘ │  │ └──────────┘ │
     │ ┌───────┐ │  │          │  │ ┌──────────┐ │
     │ │情绪    │ │  │          │  │ │风控经理   │ │
     │ └───────┘ │  │          │  │ └──────────┘ │
     └───────────┘  └──────────┘  └──────────────┘
            │            │            │
            └────────────┴────────────┘
                    消息总线
              （子智能体之间的通信通道）
```

### 2.2 子智能体的生命周期（参考 learn-claude-code s09）

```
每个子智能体有以下状态:

  IDLE（空闲）→ 收到任务 → WORKING（工作中）→ 完成任务 → IDLE
                                              ↓ 失败
                                           ERROR（报错）
                                              ↓
                                           IDLE（重试）

通信方式:
  - 收件箱（inbox）: 其他智能体发来的消息
  - 广播（broadcast）: 向所有智能体发消息
  - 私信（send）: 向指定智能体发消息
```

## 三、通信机制设计（三种方案）

### 方案A: 简单管道（最容易实现）

```
父智能体充当"邮递员":

  父 → 派活给技术分析师 → 收到报告
  父 → 把报告转给基本面分析师 → 收到报告
  父 → 把所有报告转给看多 → 收到论点
  父 → 把看多论点转给看空 → 收到反驳
  父 → 把辩论记录转给研究经理 → 收到裁决
  ...

通信方式: 子智能体之间不直接通信，所有消息通过父智能体中转

优点: 实现简单，可控
缺点: 子智能体之间不能直接对话，辩论不够自然

参考: learn-claude-code s04（子代理模式）
```

### 方案B: 消息总线（推荐方案）

```
子智能体之间可以直接通信:

  消息总线（MessageBus）= 一个共享的消息队列

  看多智能体:
    inbox = ["看空的论点: PE偏高..."]
    → 读取inbox
    → 生成反驳
    → send("bear-debater", "虽然PE偏高但PEG合理...")

  看空智能体:
    inbox = ["看多的反驳: 虽然PE偏高但PEG合理..."]
    → 读取inbox
    → 生成反驳
    → send("bull-debater", "但增长正在放缓...")

通信方式:
  - send(target, message): 给指定智能体发消息
  - broadcast(message): 给所有智能体发消息
  - read_inbox(): 读取自己的收件箱

优点: 辩论自然，智能体之间直接交流
缺点: 需要管理消息队列，防止死循环

参考: learn-claude-code s09（团队通信）+ JSONL收件箱
```

### 方案C: 自组织团队（最灵活，最复杂）

```
子智能体自己看任务板，有活就干:

  共享任务板:
    任务1: 分析300033技术面 → [已认领: 技术分析师]
    任务2: 分析300033基本面 → [已认领: 基本面分析师]
    任务3: 辩论: 300033是否值得投资 → [待认领]
    任务4: 风控评估 → [待认领]

  每个智能体空闲时轮询任务板:
    → 发现任务3未认领，且自己是看多研究员 → 认领
    → 执行任务 → 完成后标记完成

优点: 完全自组织，最灵活
缺点: 实现复杂，可能有冲突

参考: learn-claude-code s11（自主代理）
```

## 四、推荐架构（方案B — 消息总线）

### 4.1 为什么推荐方案B

```
方案A（简单管道）: 太死板，跟现在的LangGraph没本质区别
方案B（消息总线）: 平衡了灵活性和可控性 ← 推荐
方案C（自组织）:   太复杂，对股票分析场景过度设计
```

### 4.3 一次完整分析的执行流程

```
第1阶段: 数据收集（可并行）

  父智能体:
    spawn_agent("technical-analyst", "分析300033技术面")
    spawn_agent("fundamentals-analyst", "分析300033基本面")
    spawn_agent("news-analyst", "分析300033新闻")
    spawn_agent("sentiment-analyst", "分析300033情绪")

  各子智能体并行执行:
    技术分析师: load_skill → 调工具 → 写报告 → send给父智能体
    基本面分析师: load_skill → 调工具 → 写报告 → send给父智能体
    新闻分析师: load_skill → 调工具 → 写报告 → send给父智能体
    情绪分析师: load_skill → 调工具 → 写报告 → send给父智能体

  父智能体: 收集4份报告 → 转发给研究团队

第2阶段: 多空辩论（子智能体直接通信）

  父智能体:
    spawn_agent("bull-debater", "为300033建立看多论证")
    spawn_agent("bear-debater", "为300033建立看空论证")
    send("bull", 4份报告)  ← 同时给双方发报告
    send("bear", 4份报告)

  辩论过程（通过消息总线直接通信）:
    看多 → send("bear", "增长潜力大，营收增25%...")
    看空 → read_inbox → send("bull", "但PE偏高，利润增速放缓...")
    看多 → send("bear", "PEG仅1.8，估值合理...")
    （达到轮次上限后停止）

  父智能体:
    收集辩论记录
    spawn_agent("research-manager", "裁决辩论")
    send("research-manager", 4份报告 + 辩论记录)
    研究经理: load_skill → 思考 → 输出投资计划

第3阶段: 交易决策

  父智能体:
    spawn_agent("trader", "基于投资计划出交易建议")
    send("trader", 投资计划 + 4份报告)
    交易员: load_skill → 输出买卖建议 + 目标价 + 信心分

第4阶段: 风控辩论（子智能体直接通信）

  父智能体:
    spawn_agent("aggressive-risk", ...)
    spawn_agent("conservative-risk", ...)
    spawn_agent("neutral-risk", ...)
    send给三方: 交易建议 + 4份报告
    spawn_agent("risk-manager", ...)

  风控辩论（通过消息总线直接通信）:
    激进 → broadcast("高收益视角...")
    保守 → broadcast("风险太大...")
    中性 → broadcast("平衡观点...")
    （达到轮次后）

  风控经理: 综合全部信息 → 最终决策
  父智能体: 输出最终结果 → "买入/持有/卖出"
```

## 五、三种实现层级（从简单到复杂）

### 层级1: 最小可用版（MVP）— 推荐

```
只用 learn-claude-code 的 s04（子代理）模式:

  - 父智能体创建子智能体执行任务
  - 子智能体之间不直接通信（方案A）
  - 所有通信通过父智能体中转
  - 子智能体执行完返回结果，父智能体汇总

  代码量: ~200行
  依赖: anthropic SDK 或 其他LLM SDK
  成本: 可控（子智能体用完即销毁）

  适合: 先跑通流程，验证效果

```

  代码量: ~400行（在层级1基础上+200行）
  新增: MessageBus 类（JSONL文件实现）

  适合: 辩论效果验证，体验完整流程

  适合: 多股票并行分析场景

## 六、关键问题与思考

### 6.1 子智能体的"大脑"用什么？

```
每个子智能体都有一个 Agent Loop（while循环）

子智能体的"大脑"可以是:
  a) LLM（Claude/DeepSeek/GLM）— 灵活但花钱
  b) 纯代码（算法+模板）— 免费但死板
  c) 混合 — 分析师用代码，辩论者用LLM

推荐: 混合方案
  - 4个分析师: 用代码（已有Tushare数据接口+算法）
  - 4个辩论者: 用LLM（辩论需要语言理解）
  - 2个经理: 用LLM（裁决需要推理能力）
  - 1个交易员: 用LLM（需要综合判断）

这样只调 7-8 次LLM，而不是原来的 30-50 次
```

### 6.2 会不会陷入死循环？

```
辩论时可能出现:
  看多: "应该买"
  看空: "不应该买"
  看多: "应该买"
  看空: "不应该买"
  ... 无限循环

解决方案（learn-claude-code s10 的思路）:
  1. 设置最大轮次（max_debate_rounds）
  2. 超时机制（超过N秒强制结束）
  3. 轮次计数器（每方最多发言N次）
```

### 6.3 子智能体的上下文管理

```
每个子智能体有独立的上下文:

  技术分析师的上下文: 只有技术分析相关的数据
  看多研究员的上下文: 4份报告 + 辩论历史

优点:
  - 互不干扰（不会"串台"）
  - 节省token（每个人只看自己需要的数据）

参考: learn-claude-code s04 "干净的上下文"
  "子代理用全新的messages=[]启动，
   子代理可能跑了30+次工具调用，
   但父代理只收到一段摘要"
```

### 6.4 Skill 如何融入

```
每个子智能体启动时加载对应的 Skill:

  spawn_agent("technical-analyst")
    → 子智能体启动自己的 Agent Loop
    → load_skill("technical-analyst/SKILL.md")
    → 按Skill的指引执行任务
    → 完成后返回摘要给父智能体

Skill = 角色说明书 + 工作流程 + 输出模板
子智能体 = 读了说明书的员工，自己决定怎么干活
```
